## Bug Fixes

- **Security: admin endpoints accepted sessions of any realm.** `AdminAuth` matched a session's username and login scheme against admin logins without checking the realm, so a user of any realm named like an admin acted as that admin on `/admins`, `/realms` and the machine-auth endpoints. It now maps only sessions opened on the admin realm `_` (`401` otherwise).
- **Security: `/sessions/*` had no authorization (breaking).** Any valid session could read, list and delete any other session and read its `cookie_string`, the session credential. A caller now acts on its own sessions (same realm and username, any login scheme); admins also on those of the realms they may manage (`can_manage_realm`, so the super admin loses sessions of claimed realms); `DELETE /sessions/expired` is for super admins. A session the caller may not access is reported as not found, and `DELETE /sessions` is refused as a whole if one session is not the caller's to delete.
- **Security: session responses leaked the session credential (breaking).** `/sessions` now returns `SessionInfo`, without `cookie_string`; `AuthClient::get_session` and `get_session_with_action` return it instead of `SessionData`.
- **Security: any admin could manage global machine roles.** `/auth/approle/*` and `/auth/kubernetes/*` role management (including secret IDs) is now limited to super admins through a `require_super_admin` scope guard; the login endpoints stay unauthenticated.
- **Security: a realm admin could change any admin's 2FA.** The TOTP endpoints checked the realm in the URL but wrote the 2FA of the admin record named by `username`. In the admin realm `_` they now follow the `_` login rule (the caller must manage every admin record whose `userpass` or id is the login, or be a super admin when none uses it), and in any other realm they answer `400`.
- **Security: 2FA was silently not enforced (breaking).** Login looked 2FA up by login name among admin ids, and enrolment for ordinary realm users answered "ok" while storing nothing. Login now reads the 2FA of the admin found through its login (the one `AdminAuth` uses), so admins whose id differs from their login, and JWT admins, are protected; realm users have no 2FA and enrolling them is refused with `400`.
- **Security: a realm admin could delete logins in every realm.** `userpass` was unchecked free text and deleting an admin deleted every credential of that name in every realm. `POST`/`PUT /admins` now accept a `userpass` only for a login the caller manages (`403`) and that no other admin uses (`409`), deleting an admin removes only its own `_` login (and only if no other admin uses it), and `delete_userpass_by_username` is gone from the `Database` trait.
- **Security: the super admin could take over a claimed realm through its admins' logins.** `/realms/_/*` only checked that the caller manages realm `_`, so a super admin could reset the login or the 2FA of a claimed realm's admin, or re-point an admin record by creating a login named like its id. The `_` login rule now applies to the credential and TOTP endpoints (realm admins manage their own and their colleagues' logins), auto-link no longer overwrites an existing link, and deleting a login unlinks every record using it. `GET /realms/_/userpass` is open to every admin and lists only the logins it manages.
- **Security: password hashes and 2FA secrets were returned.** The credential lists returned Argon2 hashes and `GET /admins` / `GET /admins/{id}` returned `totp_secret` and `totp_auth_url`. Hashes are cleared in every list, the 2FA secret and URL are never serialized, `totp_*` fields in `POST`/`PUT /admins` bodies are ignored (they enabled 2FA without verification), and an update keeps the stored 2FA.
- **Shared admin logins are refused.** Two admin records sharing a login make the admin lookup (and the login-time 2FA check) fail with `401` instead of picking one; the server logs a warning at startup naming them.
- **Admin logins are unique in the database.** `admin.userpass` and `admin.jwt` get unique indexes at startup (SQLite, PostgreSQL, MySQL), so two concurrent requests cannot link one login to two admins (`409`); a column that already holds shared values only logs a warning and stays non-unique, and the MySQL `jwt` index covers a 255-character prefix.
- **Super admins can read every admin.** `GET /admins` lists all admins and `GET /admins/{id}` is readable for any admin, including those of claimed realms, so the super admin can contact them; changes still follow the exclusive-ownership rule.

## Refactor

- **Breaking:** removed `POST /sessions` (create or update a session) and `UpsertSessionRequest`: nothing called them, and they let any caller write a session.
- The dev seed's optional TOTP user is now created as an admin login of the admin realm `_` (with an admin record holding the 2FA) instead of a user of the seeded realm, because 2FA only exists for admin logins.

## Tests

- New `sessions_authz_tests` covering admin endpoints with a foreign-realm session, `/sessions` for realm users, realm admins, the super admin on unclaimed and claimed realms, `cookie_string` absence, the removed `POST /sessions`, and AppRole/Kubernetes management by a realm admin.
- New `admin_logins_tests` for each finding of #130 (2FA across admins and realms, decoy and cascade deletes, takeover of a claimed realm's login, hash and secret leaks, link validation, ambiguous logins); updated the TOTP, list and get tests that encoded the old rules.

## Docs

- Authorization guide, API reference, OpenAPI, session management, client library, getting started and flows now describe the `/sessions` access rules, that a backend forwards the user's own cookie (`session_id` is the SHA-256 hex of the cookie value), and that admin sessions come from `_`; fixed the wrong "Cookie-Realm Constraint" text.
- The admin UI `SessionData` type, unused but copying the leaked field, is now `SessionInfo` without `cookie_string`.
- Authorization guide, API reference, OpenAPI and the 2FA guide describe the `_` login rule, link validation, per-login 2FA and the read access of super admins; fixed the wrong "What alice can now do" list and the "unique constraint on userpass(username)" caveat.
- The admin UI no longer sends `totp_*` fields (they are ignored and would otherwise round-trip stale values), and addresses TOTP and credentials by the admin's login name.
